# Website onboarding

Ceasar serves a responsive wizard at `/onboarding/` for signed-in native users. The web-domain list links to it. Customer enrollment providers can mount the same `createOnboardingWizard` JavaScript module and supply their own account, offer and billing operations. Ceasar does not decide plan prices, trial eligibility or card admission.

## Enrollment provider contract

`web/js/src/customer/wizard.js` exports `createOnboardingWizard`. Pass its root element, provider, authenticated account ID, offers, trial eligibility, capabilities, and callbacks for account creation, admission and refreshing offers. `mode: 'native'` uses the existing Ceasar session and omits customer identity and billing admission. `web/js/src/onboarding-native.js` is the native adapter; `web/js/src/customer/providers.js` implements the optional same-origin business API adapter.

Capabilities declare `setupMethods` entries `wordpress-new`, `wordpress-move`, `php-import` and `php-static`, each with `trial` and `paid` booleans. Optional `trialDays` and `phpVersion` describe the provider's actual offer and destination. Offers carry `planCode`, `displayName`, `currency`, `monthlyPriceMinor` (the existing `monthlyPriceCadCents` field is also accepted), `websiteLimit`, `storageBytes`, `transferBytes`, `trialAvailable` and `paidAvailable`. The provider remains responsible for eligibility and a fresh capacity check at admission and after card setup.

| Provider method                                                                                             | Responsibility                                                                                                           |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `readOnboarding(accountId)`, `saveOnboarding(accountId, draft)`                                             | Return `{draft, capabilities}` and persist typed choices for the authenticated owner.                                    |
| `requestTrialAdmission(input)`, `requestPaidAdmission(input)`                                               | Admit an idempotent commercial request and return its request/service IDs, progress and optional hosted `checkoutUrl`.   |
| `setupCheckout(accountId, requestId)`                                                                       | Resume the same pending hosted checkout.                                                                                 |
| `serviceOnboarding(accountId, serviceId)`                                                                   | Return current native progress with `operationId`, `status`, `stage`, `message`, `nextAction` and optional `previewUrl`. |
| `hostingAccess(accountId, serviceId)`                                                                       | Return an authorized single-use POST grant.                                                                              |
| `wordpressAccess(accountId, serviceId, userId)`                                                             | Return a short-lived URL for the selected existing administrator, or normal login.                                       |
| `confirmMigration(serviceId, input)`                                                                        | Record the owner's completed restore and check native readiness.                                                         |
| `domainStatus(accountId, serviceId, domain)`, `connectDomain(accountId, serviceId, domain, idempotencyKey)` | Return exact DNS records and the persisted connection/certificate state for the existing website.                        |

Drafts contain the current step, website method/type/intent, selected plan/payment mode, title, administrator email or selected imported administrator, domain, service ID and request ID. The browser adapter translates the wizard's method names to the backend draft schema. Reject unknown fields and cross-account references on the server. Never include passwords, tokens, payment details, grants or checkout URLs. Browser storage can preserve pre-authentication choices; authenticated resume must use the server draft. Keep operation IDs and idempotency keys stable when a response is lost.

## Native operation API

The root-trusted API profile permits `v-onboarding-request USER ACTION BASE64_JSON`. The JSON argument is standard Base64 of a JSON object, with a decoded limit of 24 KiB. The command refuses non-root execution. Native browser requests go through `/onboarding/api/`; this endpoint takes the user from the authenticated Ceasar session, validates CSRF and invokes the same command. It does not accept a caller-supplied tenant, node, command or filesystem path.

| Action                            | Input                                                                                                                                    | Result                                                      |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `read-draft`, `save-draft`        | An allowlisted draft object for save                                                                                                     | Saved selection and capabilities                            |
| `prepare`                         | `idempotencyKey`, `hostname`, `siteType` (`wordpress`, `php`, `static`), `intent` (`new_site`, `migration`), `siteTitle`, `contactEmail` | Durable operation progress                                  |
| `status`, `retry`                 | `operationId`                                                                                                                            | Current operation progress                                  |
| `wordpress-access`                | `hostname`, `administrator` or `userId`                                                                                                  | Single-use WordPress URL, or normal login URL               |
| `create-grant`                    | `hostname`, `destination` (`dashboard`), optional configured `sourceOrigin`                                                              | `actionUrl`, `token`, `expiresAt`                           |
| `domain-status`, `connect-domain` | `hostname`, `domain`                                                                                                                     | Exact DNS records, verification and certificate state       |
| `confirm-migration`               | `operationId`                                                                                                                            | Verified local readiness after the owner confirms an import |

Progress includes `operationId`, `hostname`, `siteType`, `intent`, `status`, `stage`, `message` and `nextAction`. `status` is `queued`, `running`, `needs_action`, `ready` or `failed`. A WordPress migration reaches `needs_action` at stage `transfer` when the destination and WPvivid tools are usable; it becomes `ready` after import confirmation and a local WordPress check. PHP import reaches `needs_action` when its file/database workspace is available. The caller should keep the same idempotency key on retries and poll `status` rather than submit another site request. A failed operation can use `retry`; a partial WordPress installation requires reconciliation before retrying. Commercial admission remains with the provider.

The root-owned SQLite ledger lives at `/var/lib/ceasar/onboarding/operations.sqlite`. `prepare` binds the operation ID and website selection to the server draft in the same transaction, so a lost response can resume by reading the draft. Replaying the same operation preserves later wizard progress. `ceasar-onboarding.timer` starts the bounded PHP worker every minute. It picks one operation, checks native Ceasar state before creating a site, and can resume after process restart. WordPress operations run as the owning tenant. The package installer and upgrade hook install and enable the worker; the upgrade hook also adds only `v-onboarding-request` to an existing `iharc-control` API profile.

To rerun the native fixture from the repository root on a Docker host, run the following command for each of `native-operations`, `native-session` and `customer-csp` (substitute the test name). It uses a read-only checkout and no network:

```sh
docker run --rm --network none -v "$PWD:/src:ro" -v "$PWD/tests/onboarding/bin:/usr/local/ceasar/bin:ro" -v "$PWD/tests/onboarding/onboarding.json:/usr/local/ceasar/conf/onboarding.json:ro" -w /src php:8.3-cli php tests/onboarding/native-operations.php
```

## WordPress and domains

New sites use Ceasar's standard `v-quick-install-app` WordPress installer. The worker passes `generate_password=true`; the installer creates the administrator password internally, keeping it out of the worker's command arguments. Existing explicit-password installs remain supported. The worker applies the requested title and administrator email to new installations. It leaves restored site content, plugins, themes and users alone. Migration preparation installs WPvivid Backup & Migration version `0.9.136` on the destination; the customer uses WPvivid's supported transfer or backup-upload interface. The optional WP-CLI login package is pinned to `aaemnnosttv/wp-cli-login-command` `v1.5.0` and installs its companion plugin. If it is unavailable or disabled, the customer uses `wp-login.php`. After restoring a site, the customer selects an existing administrator; Ceasar creates no hidden imported-site administrator.

`domain-status` supplies apex A/AAAA records, a `www` CNAME and a per-tenant/site/domain TXT challenge at `_ceasar-verification.<domain>`. A shared-node A record alone does not prove ownership. Ceasar checks the exact TXT value and rejects conflicting web addresses before it queues domain connection. Its native alias command enforces global domain uniqueness. The worker obtains a certificate and probes HTTPS at the site's configured public address, using the customer domain for SNI, certificate validation and the HTTP Host header. It then exports a WordPress database backup into the owning website's private directory and performs a repeatable WP-CLI URL replacement. The preview hostname and original site remain available until cutover. DNS changes are made at the customer's provider; Ceasar never asks for registrar credentials or edits mail records.

For a native Ceasar user, the website hostname may itself be the customer domain. That primary hostname still requires DNS and TXT verification, but Ceasar does not add it as an alias to itself. Certificate issuance may include a verified `www` alias when its DNS is ready.

## Access and CAPTCHA configuration

`/usr/local/ceasar/conf/onboarding.json` is protected installation configuration. `v-setup-onboarding-runtime` initializes its `panel_origin` from a qualified system hostname when available. Confirm it is the exact public HTTPS panel origin, including a nonstandard port if used. Add customer account origins to `grant_origins` when the enrollment page is on another origin. These source origins must be exact; wildcards are rejected for grants. For customer portals that hand off to multiple Ceasar nodes, `access_origins` adds exact HTTPS destinations or a qualified wildcard suffix such as `https://*.nodes.example.com:8083` to the portal's CSP `form-action` only. The provider must still authorize and bind the chosen destination for each service. If the Ceasar web IP is private or behind NAT, set `public_address` to the actual public IPv4 or IPv6 address; the wizard refuses to publish private addresses as DNS instructions. `create-grant` accepts `sourceOrigin` only from the configured list. Its token expires after 60 seconds and is consumed once by POST field `grant` at the absolute `actionUrl`; the POST Origin and destination Host must match the grant. The handoff starts an ordinary restricted Ceasar session through the same bootstrap as password login. Do not put grants in drafts, URLs or analytics.

Create Cloudflare Turnstile widgets in Managed mode. For native login and recovery, set `/usr/local/ceasar/conf/turnstile.json` (root-owned, group `ceasarweb`, mode `0640`) with `enabled`, `site_key`, `secret_key` and exact `hostname`. The default file disables CAPTCHA. Native auth sends each token once to Cloudflare Siteverify and checks its hostname and action (`native_login` or `native_recovery`). The browser receives only the site key. For customer enrollment, set `turnstile_site_key` in protected `customer.json`, configure the same site key and secret with the Supabase Auth CAPTCHA integration, and enable enforcement there after the frontend and keys are installed. Customer auth passes tokens to Supabase once; Ceasar does not Siteverify them a second time. No keys are shipped in the public package.

Native CAPTCHA configuration uses `enabled`, `site_key`, `secret_key`, and an explicit `hostnames` list in `conf/turnstile.json`. Include every public hostname that serves native login or reset, including reverse proxy hostnames. Never derive this allowlist from a request header. The single-host `hostname` field remains supported. Cloudflare must allow the same hostnames; native verification checks the configured hostname and authentication action.
